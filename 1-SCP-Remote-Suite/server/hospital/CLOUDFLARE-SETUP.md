# เชื่อม SCP-Remote ออกอินเทอร์เน็ตด้วย Cloudflare Tunnel — ทีละขั้น

คู่มือลงมือทำ สำหรับผู้ดูแลระบบโรงพยาบาล เขียน **23 กันยายน 2569**

เอกสารนี้คือ "ทำยังไง" ส่วนเหตุผลเบื้องหลังและทางเลือกอื่นอยู่ใน [REMOTE-OVER-INTERNET.md](REMOTE-OVER-INTERNET.md)

อ่านจบแล้วทำตามได้เลย ใช้เวลาประมาณ 40–60 นาที **ยกเว้นขั้นที่ 1–2 ที่ควรทำก่อนล่วงหน้า**

---

## ภาพรวม: มันทำงานยังไง

```
เจ้าหน้าที่ที่บ้าน                Cloudflare                  เซิร์ฟเวอร์ รพ.
   เบราว์เซอร์  ──────►  remote.kpsnana.com  ──────►  cloudflared ──► localhost:8443
                          (ถาม Access ก่อน)          (ต่อออกจากข้างใน)
```

**จุดสำคัญที่ทำให้วิธีนี้ปลอดภัยกว่า port forward:** `cloudflared` เป็นฝ่าย **ต่อออก** ไปหา Cloudflare ไม่มีใครต่อ **เข้า** มาที่ไฟร์วอลล์โรงพยาบาลเลย พอร์ตขาเข้ายังปิดสนิทเหมือนเดิมทุกพอร์ต

---

## สิ่งที่ต้องมี (มีครบแล้วทั้งหมด)

| | สถานะ |
| --- | --- |
| บัญชี Cloudflare | ✅ `your-email@example.com` |
| โดเมน | ✅ `kpsnana.com` |
| `cloudflared` ติดตั้งบนเซิร์ฟเวอร์ | ✅ รุ่น 2026.8.3 ทำงานอยู่ |
| Tunnel ที่ต่อติดแล้ว | ✅ ใช้กับระบบจองคิว/เรียนออนไลน์อยู่ |
| อินเทอร์เน็ตขาออก | ✅ ต่อ Cloudflare ได้ ไม่มีพร็อกซีขวาง |

## ⛔ ข้อห้ามสองข้อ อ่านก่อนเริ่ม

1. **ห้าม `Stop-Service Cloudflared`** — tunnel ตัวนี้กำลังให้บริการระบบจองคิวที่ประชาชนใช้อยู่ การหยุดเพื่อไล่ปัญหา SCP-Remote จะล้มระบบจองคิวไปด้วย
2. **ห้ามแตะไฟล์ `agentserver-cert-*`** ใน `.local/scp-remote/` — เครื่องลูก 102 เครื่องผูกกับแฮชของไฟล์นี้ ถ้าเปลี่ยนต้องเดินไปลงเอเจนต์ใหม่ทีละเครื่อง (ใบรับรองเว็บเป็นคนละใบ แตะได้)

## ⏱️ ลำดับสำคัญมาก — อย่าสลับ

เหตุผล: ถ้าเพิ่ม route ก่อนตั้ง Access จะมี**ช่วงเวลาที่เซิร์ฟเวอร์โรงพยาบาลเปิดสู่อินเทอร์เน็ตโดยมีแค่รหัสผ่านกั้น** อาจแค่ไม่กี่นาที แต่บอตสแกนหาเว็บใหม่ตลอดเวลา

ลำดับด้านล่างออกแบบมาให้**ไม่มีช่วงเปิดโล่งเลยสักวินาที** — สร้าง Access ให้เสร็จก่อน แล้วค่อยเปิดประตู

## ขั้นที่ 1 — เปิด 2FA บัญชี Cloudflare

ทำก่อนเพราะบัญชีนี้กำลังจะกลายเป็นกุญแจของคอมพิวเตอร์ 102 เครื่อง ใครเข้าบัญชีนี้ได้ สามารถแก้ route ให้ชี้ไปไหนก็ได้ หรือลบ Access policy ทิ้งได้ทั้งหมด **โดยไม่ต้องแตะเซิร์ฟเวอร์เลย**

1. เข้า [dash.cloudflare.com](https://dash.cloudflare.com/) → คลิกรูปคนมุมขวาบน → **My Profile**
2. แท็บ **Authentication**
3. หัวข้อ **Two-Factor Authentication** → **Enable**
4. สแกน QR ด้วย Google Authenticator / Microsoft Authenticator
5. ใส่เลข 6 หลักเพื่อยืนยัน
6. **คัดลอก recovery codes เก็บไว้ที่ปลอดภัยนอกเครื่อง** (พิมพ์ใส่กระดาษเก็บในตู้เอกสาร หรือใส่ password manager — อย่าเก็บไว้ในเครื่องเดียวกับที่ใช้ Authenticator)

> อีเมล `your-email@example.com` ก็ควรเปิด 2FA ด้วย เพราะรีเซ็ตรหัสผ่าน Cloudflare ผ่านอีเมลได้

## ขั้นที่ 2 — เปิด 2FA บัญชี admin ของ SCP-Remote

1. เปิด `https://192.168.2.25:8443` แล้วล็อกอินด้วย `admin`
2. มุมขวาบน → **บัญชีของฉัน** (My Account)
3. หา **Two-Factor Authentication / การยืนยันตัวตนสองขั้น** → เพิ่ม **Authenticator App**
4. สแกน QR แล้วใส่เลขยืนยัน
5. สร้าง **backup codes** แล้วเก็บไว้นอกเครื่องเช่นกัน
6. **ทดสอบ:** ล็อกเอาต์แล้วล็อกอินใหม่ ต้องถามเลข 6 หลัก

ตรวจว่าระบบเห็นแล้ว:

```
npm run tunnel:mode
```

ต้องขึ้นว่า `บัญชีผู้ใช้ : ตั้ง 2FA ครบทุกบัญชีแล้ว ✅` ถ้ายังขึ้นชื่อบัญชีอยู่ แปลว่ายังไม่สำเร็จ อย่าไปต่อ

> **ทำไมต้องทำก่อน:** ขั้นที่ 4 จะบังคับ 2FA ทั้งเซิร์ฟเวอร์ ถ้าบัญชียังไม่ลงทะเบียน จะล็อกตัวเองออกจากเซิร์ฟเวอร์ตัวเอง — สคริปต์จะปฏิเสธไม่ให้ทำ แต่รู้ไว้ว่าทำไม

## ขั้นที่ 3 — ดู tunnel เดิม (ดูอย่างเดียว ห้ามแก้)

1. [dash.cloudflare.com](https://dash.cloudflare.com/) → เมนูซ้าย **Networking** → **Tunnels**
2. จะเห็น tunnel ที่มีอยู่ สถานะควรเป็น **HEALTHY**
3. คลิกเข้าไปดูแท็บ **Routes** — จดไว้ว่าตอนนี้มี hostname อะไรบ้าง (ระบบจองคิว/เรียนออนไลน์)

**จดชื่อ tunnel ไว้** จะใช้ในขั้นที่ 7

> เราจะ**เพิ่ม** route ใหม่เข้าไปใน tunnel เดิม ไม่ได้แก้ของเดิม แต่ละ route เป็นอิสระต่อกัน ระบบจองคิวไม่กระทบ

## ขั้นที่ 4 — ฝั่งเซิร์ฟเวอร์

ที่เครื่องเซิร์ฟเวอร์ เปิด PowerShell ในโฟลเดอร์ `F:\EX\sichomphu-remote`

```
npm run tunnel:mode enable
```

สคริปต์จะ:
- สำรองไฟล์ตั้งค่าเดิมไว้ให้อัตโนมัติ
- ตั้ง `trustedProxy` = `127.0.0.1` (เพื่อให้ log บันทึก IP จริงของผู้ใช้ ไม่ใช่ loopback)
- เปิด allowlist (เพราะ IP บ้านของเจ้าหน้าที่ไม่มีวันอยู่ในลิสต์)
- บังคับ 2FA
- **ไม่แตะไฟร์วอลล์** — tunnel เข้าทาง loopback ไม่ต้องเปิดพอร์ต

ถ้ายังมีบัญชีไม่ได้ตั้ง 2FA มันจะ**ปฏิเสธและไม่แก้ไฟล์เลย** พร้อมบอกชื่อบัญชี

จากนั้น

```
npm run check:config
npm run service:restart
```

`check:config` ต้องไม่ขึ้นคำว่า **"ยังไม่พร้อมเปิดใช้"**

**ยืนยันว่า restart เกิดขึ้นจริง** (ข้อความ "started" เชื่อไม่ได้ เคยหลอกมาแล้ว)

```powershell
Get-NetTCPConnection -LocalPort 8443 -State Listen | Select-Object OwningProcess
```

PID ต้องเปลี่ยนจากเดิม

> ตอนนี้เซิร์ฟเวอร์พร้อมรับจากภายนอกแล้ว **แต่ยังไม่มีใครเข้าถึงได้** เพราะยังไม่มี route ชี้มา

## ขั้นที่ 5 — Access: ปล่อย 4 เส้นทางของเอเจนต์ก่อน

**นี่คือขั้นที่คนทำพลาดกันมากที่สุด**

เอเจนต์บนเครื่องลูกไม่มีเบราว์เซอร์ ล็อกอินอีเมลไม่ได้ ถ้าเอา Access ครอบทั้งโดเมนโดยไม่ยกเว้นเส้นทางพวกนี้ ผลคือ **เครื่องขึ้นออนไลน์ครบทุกเครื่อง แต่กดรีโมตแล้วหน้าจอไม่ขึ้นสักเครื่อง** — อาการจะเหมือนระบบรีโมตเสีย ไม่มีใครเดาว่าเป็นเพราะ policy

เส้นทางที่ต้องยกเว้น (ตรวจจากโค้ดจริงแล้ว ไม่ใช่แค่ `agent.ashx`):

| เส้นทาง | ใช้ทำอะไร |
| --- | --- |
| `/agent.ashx` | ช่องสัญญาณหลักของเอเจนต์ |
| `/meshrelay.ashx` | เอเจนต์ต่อเข้ามาเองตอนเปิดหน้าจอ/เทอร์มินัล |
| `/agenttransfer.ashx` | รับ–ส่งไฟล์ |
| `/agentdownload.ashx` | เอเจนต์ดึงโมดูลรุ่นใหม่ |

**ทำ 4 รอบ รอบละเส้นทาง:**

1. **Zero Trust** → **Access controls** → **Applications** → **Add an application** → **Self-hosted**
2. **Application name:** เช่น `SCP-Remote agent channel`
3. **Domain:** `remote` . `kpsnana.com` **Path:** `agent.ashx`
4. เพิ่ม policy:

   | Action | Rule type | Selector | Value |
   | --- | --- | --- | --- |
   | **Bypass** | Include | Everyone | Everyone |

5. Save

ทำซ้ำกับ `meshrelay.ashx`, `agenttransfer.ashx`, `agentdownload.ashx`

> **ข้อควรรู้:** Cloudflare ระบุว่า Bypass **ไม่บันทึก log ของ Access** สำหรับเส้นทางนั้น ไม่เป็นไรเพราะ MeshCentral บันทึกเองอยู่แล้ว และเส้นทางเหล่านี้ยังมีการยืนยันตัวตนของ MeshCentral เอง (ใบรับรองเอเจนต์ / คุกกี้ relay) การ bypass แค่ไม่บังคับ "ล็อกอินอีเมล" ซึ่งเอเจนต์ทำไม่ได้อยู่แล้ว
>
> **อย่า bypass เส้นทางอื่นนอกจาก 4 ตัวนี้** โดยเฉพาะ `/` ซึ่งเป็นหน้าเว็บหลัก

### ตรวจว่า bypass ได้ผลจริง — ไม่ต้องเดา

รันจากเครื่องไหนก็ได้ที่ออกอินเทอร์เน็ตได้ **สิ่งที่ดูคือมี `cloudflareaccess` ในหัว `location` หรือไม่** ไม่ใช่ดูรหัส HTTP

```bash
for p in "/" "/agent.ashx" "/meshrelay.ashx" "/agenttransfer.ashx" "/agentdownload.ashx"; do
  curl -sI "https://remote.kpsnana.com${p}" | head -1
  curl -sI "https://remote.kpsnana.com${p}" | grep -i "^location:" | grep -c cloudflareaccess
done
```

ผลที่ถูกต้อง (ตรวจแล้วเมื่อ 23 ก.ย. 2569):

| เส้นทาง | HTTP | Access แทรก |
| --- | --- | --- |
| `/` | 302 | **ใช่** — ถูกต้อง หน้าเว็บต้องล็อกอินก่อน |
| `/agent.ashx` | 404 | ไม่ |
| `/meshrelay.ashx` | 404 | ไม่ |
| `/agenttransfer.ashx` | 404 | ไม่ |
| `/agentdownload.ashx` | 404 | ไม่ |

**404 คือคำตอบที่ถูกต้อง** เส้นทางเหล่านี้เป็น websocket การเปิดด้วย GET ธรรมดาจึงได้ 404 จาก MeshCentral — สิ่งสำคัญคือมัน**ไปถึง MeshCentral** ไม่ได้ถูก Access ดักไว้ก่อน

**ทดสอบเทียบด้วยเสมอ** ลองเส้นทางที่ไม่ได้ bypass เช่น `/notbypassed.ashx` ต้องได้ **302 + Access แทรก** ถ้าเส้นทางนั้นก็ได้ 404 เหมือนกัน แปลว่า bypass กว้างเกินไปและหน้าเว็บอาจไม่ได้ถูกกั้นจริง

## ขั้นที่ 6 — Access: ล็อกหน้าเว็บทั้งโดเมน

1. **Add an application** → **Self-hosted** อีกครั้ง
2. **Application name:** `SCP-Remote`
3. **Domain:** `remote` . `kpsnana.com` (คราวนี้**ไม่ใส่ path**)
4. เพิ่ม policy:

   | Action | Rule type | Selector | Value |
   | --- | --- | --- | --- |
   | **Allow** | Include | Emails | อีเมลเจ้าหน้าที่ที่ละคน |

   ใส่อีเมลเป็นรายคน หรือใช้ **Emails ending in** ถ้ามีโดเมนอีเมลของโรงพยาบาล

5. Save

> application ที่ไม่มี policy เลยจะ **ปฏิเสธทุกคำขอ** ฉะนั้นอย่าลืมใส่ policy
>
> path ที่เจาะจงกว่าชนะ — 4 รายการจากขั้นที่ 5 จะยังผ่านได้ แม้รายการนี้ครอบทั้งโดเมน

## ขั้นที่ 7 — เปิดประตู: เพิ่ม route

**Networking** → **Tunnels** → เลือก tunnel ของคุณ → **Routes** → **Add route** → **Published application**

| ช่อง | ค่าที่ต้องกรอก |
| --- | --- |
| **Subdomain** | `remote` |
| **Domain** | `kpsnana.com` |
| **Path** | **เว้นว่าง** |
| **Service URL** | `https://localhost:8443` |

แล้วกาง **Additional application settings** → หัวข้อ **TLS**

| ช่อง | ค่า |
| --- | --- |
| **CA Pool** | `C:\ProgramData\cloudflared\scp-remote-root.crt` |
| **Origin Server Name** | **เว้นว่าง** |
| **Disable TLS certificate verification** | **ปิดไว้** |

กด **Add route**

> **Path ต้องเว้นว่าง** ช่องนี้เป็นตัวกรองว่าคำขอแบบไหนจะถูกส่งมาที่บริการนี้ (ใส่ได้เป็น regex เช่น `^/blog`) ถ้าใส่อะไรลงไป คำขออื่นที่ไม่ตรงจะไม่ถึงเซิร์ฟเวอร์ — เราต้องการให้ทุกคำขอมาถึง MeshCentral
>
> **ทำไมใช้ `localhost` ไม่ใช่ `127.0.0.1`:** ใบรับรองของเซิร์ฟเวอร์มี SAN เป็น `DNS Name=localhost` อยู่แล้ว จึงตรวจสอบผ่านได้ตรง ๆ ส่วนการใส่หมายเลข IP ลงช่อง Origin Server Name นั้น TLS ไม่อนุญาตให้ใช้ IP เป็น SNI (RFC 6066 กำหนดให้เป็นชื่อโฮสต์เท่านั้น) จึงเลี่ยงปัญหานี้ด้วยการใช้ชื่อไปเลย
>
> **ทำไมไม่ต้องปิดการตรวจ TLS:** ใบรับรองออกโดย `MeshCentralRoot-e68095` ซึ่งอยู่ในไฟล์ `root-cert-public.crt` ของ MeshCentral — ชี้ CA Pool ไปที่สำเนาของไฟล์นั้นก็ตรวจผ่านครบ เอกสาร Cloudflare ระบุชัดว่า `noTLSVerify` ควรใช้เป็นทางออกชั่วคราวเท่านั้น
>
> **ถ้าไม่ใส่ CA Pool จะได้ 502** เพราะ "Using defaults" แปลว่าให้ตรวจด้วยชุด CA สาธารณะ ซึ่งไม่รู้จักใบรับรองที่ MeshCentral ออกเอง — cloudflared จึงปฏิเสธการต่อเข้าเซิร์ฟเวอร์
>
> **สำเนาใบรับรองวางไว้ที่ `C:\ProgramData\cloudflared\` แล้ว** ไม่ชี้เข้าไปในโฟลเดอร์ `.local` ของโปรเจกต์ เพราะ path นั้นอาจย้ายตอนย้ายเซิร์ฟเวอร์ และโฟลเดอร์นั้นมีไฟล์ลับปนอยู่ ไฟล์ใบรับรองสาธารณะตัวนี้ไม่เป็นความลับ
>
> **ถ้าออกใบรับรองเซิร์ฟเวอร์ใหม่** ต้องคัดลอกทับสำเนานี้ด้วย มิฉะนั้น tunnel จะขึ้น 502 อีก:
> ```powershell
> Copy-Item F:\EX\sichomphu-remote\.local\scp-remote\root-cert-public.crt C:\ProgramData\cloudflared\scp-remote-root.crt -Force
> ```

DNS record จะถูกสร้างให้อัตโนมัติ ไม่ต้องไปเพิ่มเอง

## ขั้นที่ 8 — ทดสอบ

**ทดสอบจากมือถือที่ปิด WiFi** (ใช้เน็ตมือถือ) เพื่อให้แน่ใจว่าออกไปนอกโรงพยาบาลจริง

1. เปิด `https://remote.kpsnana.com`
2. ต้องเจอ**หน้าล็อกอินของ Cloudflare Access ก่อน** (ไม่ใช่หน้า SCP-Remote)
   - ถ้าเห็นหน้า SCP-Remote เลย → Access ไม่ทำงาน **หยุดและแก้ก่อน**
3. ล็อกอินด้วยอีเมลที่ใส่ไว้ → รับรหัสทางอีเมล → ผ่านเข้ามา
4. เจอหน้า SCP-Remote → ล็อกอิน `admin` + รหัส 6 หลักจาก Authenticator
5. **ตรวจว่าเครื่องยังออนไลน์ครบ** — ถ้าเครื่องหายไปหมด แปลว่า bypass ขั้นที่ 5 ไม่ถูกต้อง
6. **ลองรีโมตเครื่องหนึ่งเครื่อง** — ถ้าเครื่องขึ้นออนไลน์แต่หน้าจอไม่มา แปลว่า `/meshrelay.ashx` ไม่ได้ bypass

ตรวจที่เซิร์ฟเวอร์ว่าบันทึก IP จริงหรือไม่ (ไม่ใช่ `127.0.0.1`)

```
หน้าเว็บ → เหตุการณ์ → ดูรายการ "Account login from ..."
```

ถ้าขึ้น `127.0.0.1` แปลว่า `trustedProxy` ไม่ทำงาน — log จะใช้สืบไม่ได้ ต้องแก้ก่อนใช้งานจริง

## ขั้นที่ 9 — ย้ายเครื่องนอกโรงพยาบาล ⚠️ ทางเลือก ส่วนใหญ่ไม่ต้องทำ

> **ถ้าความต้องการคือ "ผู้ดูแลรีโมตเข้ามาจากข้างนอก" อย่างเดียว — จบที่ขั้นที่ 8 ไม่ต้องทำขั้นนี้**
>
> เครื่องในโรงพยาบาลต่อกับเซิร์ฟเวอร์ทาง LAN อยู่แล้ว ส่วนผู้ดูแลเข้ามาทาง tunnel ทั้งสองฝั่งเจอกันที่เซิร์ฟเวอร์ **ไม่ต้องแตะเครื่องลูกสักเครื่อง**
>
> ขั้นนี้จำเป็นเฉพาะเมื่อ **ตัวเครื่องคอมพิวเตอร์เอง** อยู่นอกโรงพยาบาลถาวร (รพ.สต.) หรือถูกเอาออกไปใช้ข้างนอกเป็นประจำ — เครื่องพวกนั้นหา `192.168.2.25` ไม่เจอ

**เฉพาะเครื่องที่อยู่นอก รพ. (รพ.สต. / โน้ตบุ๊กที่เอาออกไป)** และต้องทำ **ขณะที่เครื่องนั้นยังต่ออยู่ในเครือข่ายโรงพยาบาล**

หน้าเว็บ → เลือกเครื่อง → แท็บ **คอนโซล** → พิมพ์ทีละบรรทัด

```
msh set MeshServer "wss://remote.kpsnana.com/agent.ashx"
service restart
```

**เครื่องในโรงพยาบาลไม่ต้องแตะ** ปล่อยให้ใช้ `wss://192.168.2.25:8443/agent.ashx` ต่อไป — ถ้าย้ายไปใช้โดเมนสาธารณะ ภาพหน้าจอของเครื่องที่อยู่ห่างกันสองเมตรจะวิ่งออกอินเทอร์เน็ตไปกลับ กินเน็ตขาออกของโรงพยาบาลและช้าลงโดยไม่ได้อะไร

> ทำทีละเครื่อง ตรวจว่าเครื่องกลับมาออนไลน์ก่อนค่อยทำเครื่องถัดไป ถ้าสั่งผิดตอนเครื่องอยู่ข้างนอกแล้ว จะติดต่อกลับไม่ได้อีก ต้องเดินไปหา

## 🔙 ถ้าพัง — ย้อนกลับ

**ฝั่งเซิร์ฟเวอร์** (คืน allowlist เดิมทั้งหมด)

```
npm run tunnel:mode disable
npm run service:restart
```

**ฝั่ง Cloudflare** — ลบ route `remote.kpsnana.com` ออกจาก tunnel (route อื่นไม่กระทบ)

**เครื่องที่ย้าย URL ไปแล้ว** — ถ้ายังต่อได้ สั่งกลับผ่านคอนโซล

```
msh set MeshServer "wss://192.168.2.25:8443/agent.ashx"
service restart
```

> `tunnel:mode disable` จะ**คงการบังคับ 2FA ไว้** ตั้งใจ — ตอนนั้นทุกคนลงทะเบียนแล้ว ปิดกลับมีแต่ทำให้อ่อนลง

## ปัญหาที่พบบ่อย

| อาการ | สาเหตุที่น่าจะเป็น | แก้ยังไง |
| --- | --- | --- |
| เปิดเว็บแล้วเจอ error 502 | Service URL หรือ CA Pool ผิด | ตรวจว่าเป็น `https://localhost:8443` และ path ของ CA Pool ถูกต้อง |
| เจอหน้า SCP-Remote เลย ไม่ผ่าน Access | policy ของ application ยังไม่ได้ใส่ หรือ domain ไม่ตรง | ตรวจ Applications ว่ามี policy **Allow** อยู่จริง |
| เครื่องลูกหายไปหมด | Access ครอบ `/agent.ashx` | ตรวจว่าสร้าง Bypass ครบ 4 เส้นทาง |
| เครื่องออนไลน์ แต่หน้าจอรีโมตไม่ขึ้น | ลืม bypass `/meshrelay.ashx` | เพิ่ม Bypass ให้เส้นทางนี้ |
| ไฟล์รับส่งไม่ได้ | ลืม bypass `/agenttransfer.ashx` | เพิ่ม Bypass |
| log ขึ้น `127.0.0.1` ทุกคน | `trustedProxy` ไม่ได้ตั้ง | `npm run tunnel:mode` ดูว่า trustedProxy เป็น `127.0.0.1` |
| Tunnel ขึ้น HEALTHY แต่เว็บไม่ขึ้น | HEALTHY บอกแค่ว่า cloudflared ต่อ Cloudflare ได้ ไม่ได้ทดสอบ route | ดูแท็บ **Live logs** ของ tunnel |
| ระบบจองคิวล่ม | มีคนไปหยุด service หรือแก้ route เดิม | ห้ามหยุด service — ดูข้อห้ามด้านบน |

## หลังใช้งานจริง ควรตรวจเป็นระยะ

- **Zero Trust → Logs → Access** ดูว่าใครล็อกอินเข้ามาบ้าง มีคนพยายามเข้าที่ไม่ใช่เจ้าหน้าที่หรือไม่
- **หน้าเว็บ SCP-Remote → เหตุการณ์** ดูว่า IP ที่บันทึกเป็น IP จริง ไม่ใช่ loopback
- เมื่อเจ้าหน้าที่ลาออก **ต้องลบอีเมลออกจาก Access policy ด้วย** ไม่ใช่แค่ลบบัญชี SCP-Remote
