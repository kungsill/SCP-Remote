> ## ✅ ทำเสร็จและใช้งานจริงแล้ว — 23 กันยายน 2569
>
> `remote.kpsnana.com` เปิดใช้งานแล้ว ผ่าน Cloudflare Tunnel เดิมของโรงพยาบาล ทดสอบจากมือถือที่ใช้เน็ตมือถือ (ไม่ใช่ WiFi ของ รพ.) แล้วเปิดรีโมตเห็นหน้าจอเครื่องได้จริง
>
> ```
> Account login from 2001:44c8:41f8:1ccd:... , Chrome/153

>
> **ความต้องการจริงคือ "ผู้ดูแลรีโมตเข้ามาจากข้างนอกตอนไม่อยู่โรงพยาบาล" เท่านั้น** เครื่องทั้ง 123 เครื่องยังต่อทาง LAN ที่ `192.168.2.25:8443` ตามเดิม **ไม่ได้แตะสักเครื่อง และไม่ควรแตะ**
>
> ขั้นตอนลงมือทำอยู่ใน [CLOUDFLARE-SETUP.md](CLOUDFLARE-SETUP.md)

สำรวจและวางแผน **23 กันยายน 2569** เอกสารนี้บอกว่าต้องทำอะไร ตามลำดับไหน และอะไรที่ห้ามทำ

| ใคร | ต้องการ |
| --- | --- |

## ข่าวดี: ไม่ต้องเขียนโค้ดใหม่

MeshCentral ทำงานหลักการเดียวกับ AnyDesk อยู่แล้ว — เอเจนต์ต่อ **ออก** ไปหาเซิร์ฟเวอร์ (ไม่ใช่เซิร์ฟเวอร์ไล่ต่อเข้าเครื่อง) แล้วคุมผ่านเบราว์เซอร์ และเซิร์ฟเวอร์รันโหมด **Hybrid (LAN + WAN)** อยู่แล้ว

สิ่งที่ขาดคือ **เส้นทางจากอินเทอร์เน็ตมาถึงเซิร์ฟเวอร์** เท่านั้น

## ⛔ ต้องทำก่อน ห้ามข้าม — ทำให้บัญชีแข็งแรงพอ

ตรวจเมื่อ 23 ก.ย. 2569:

```
บัญชีทั้งหมด 1 บัญชี
  admin   ผู้ดูแลระบบเต็มสิทธิ์   2FA: ยังไม่ได้ตั้ง
force2factor: ปิด
```

**ตอนนี้ทั้งระบบกั้นด้วยรหัสผ่านอันเดียว** ตราบใดที่อยู่แต่ใน LAN ของโรงพยาบาล ความเสี่ยงยังจำกัด แต่วินาทีที่เปิดสู่อินเทอร์เน็ต รหัสผ่านที่หลุดหรือถูกเดาได้ครั้งเดียว = หน้าจอ คีย์บอร์ด ไฟล์ และ command line ของคอมพิวเตอร์ 91 เครื่องในโรงพยาบาล รวมเครื่องที่เปิดเวชระเบียนอยู่

### ลำดับที่ต้องทำ (ผิดลำดับ = ล็อกตัวเองออกจากระบบ)

1. **ตั้ง 2FA ให้บัญชี admin ก่อน** — เข้าหน้าเว็บ → บัญชีของฉัน → ตั้ง Authenticator (Google Authenticator / Microsoft Authenticator) **แล้วเก็บรหัสสำรอง (backup codes) ไว้ที่ปลอดภัยนอกเครื่อง**
2. ทดสอบล็อกเอาต์แล้วล็อกอินใหม่ด้วย 2FA ให้แน่ใจว่าใช้ได้จริง
3. สร้างบัญชีแยกให้เจ้าหน้าที่แต่ละคน **อย่าใช้ admin ร่วมกันหลายคน** — เวลามีเรื่อง จะไม่รู้ว่าใครทำ
4. ค่อยตั้ง `force2factor: true` แล้วเริ่มบริการใหม่
5. ยืนยันอีเมลของบัญชี (ตอนนี้ `your-email@example.com` ยังไม่ยืนยัน) เพื่อกู้บัญชีได้ถ้าเสียเครื่องที่มี Authenticator

> ข้อ 1–3 ต้องทำที่หน้าเว็บด้วยมือ สแกน QR แทนกันไม่ได้

## เลือกเส้นทาง

### ✅ มี Cloudflare Tunnel ที่ใช้งานจริงอยู่แล้วบนเซิร์ฟเวอร์เครื่องนี้

ตรวจพบ 23 ก.ย. 2569 ระหว่างสำรวจ และผู้ดูแลยืนยันว่าเป็นของตัวเอง ใช้กับระบบอื่นอยู่

| | |
| --- | --- |
| โปรแกรม | `C:\Program Files (x86)\cloudflared\cloudflared.exe` รุ่น 2026.8.3 |
| บริการ | ชื่อ `Cloudflared` สถานะ **Running** เริ่มอัตโนมัติ รันสิทธิ์ **LocalSystem** |
| คำสั่ง | `tunnel run --token-file C:\ProgramData\cloudflared\token` |
| ไฟล์ token | สร้างเมื่อ 5 ก.ย. 2569 |
| สถานะเชื่อมต่อ | **ต่อติดกับ Cloudflare อยู่** (QUIC 4 เส้น) ทำงานต่อเนื่องตั้งแต่ 17 ก.ย. |

เป็น tunnel แบบ **named tunnel** (ใช้ token) ซึ่งแปลว่ามีบัญชี Cloudflare อยู่แล้ว และ**การตั้งค่าว่าโดเมนไหนชี้ไปบริการใด อยู่ในแดชบอร์ด Cloudflare ไม่ได้อยู่ในเครื่องนี้** — ดูจากเซิร์ฟเวอร์ไม่ได้

### ⛔ อย่าหยุดบริการนี้

ผู้ดูแลยืนยัน 23 ก.ย. 2569 ว่า **tunnel ตัวนี้คือของตัวเอง และกำลังให้บริการระบบอื่นอยู่จริง** — ระบบเรียนออนไลน์ที่ออกเกียรติบัตร และระบบจองคิว โดยวิ่งผ่านโดเมน `kpsnana.com` ไปยังเว็บไซต์หลายตัว ตัวเลข 7.15k requests ใน 24 ชั่วโมงคือประชาชนที่กำลังใช้ระบบจองคิวอยู่

**`Stop-Service Cloudflared` = ระบบจองคิวและระบบเรียนออนไลน์ล่มทันที** อย่าสั่งเพื่อไล่ปัญหาของ SCP-Remote เด็ดขาด

### ร่องรอยที่ตรวจได้ — ยังไม่เคยชี้มาที่ SCP-Remote

การล็อกอินเข้า SCP-Remote ทั้งหมด **61 ครั้ง มาจาก `192.168.2.25` ทั้งหมด** และ **ไม่มีเหตุการณ์ใดมาจาก `127.0.0.1` เลยสักรายการ** — ถ้า tunnel ชี้มาที่เซิร์ฟเวอร์นี้ คนที่เข้ามาจะถูกบันทึกเป็น `127.0.0.1` (เพราะยังไม่ได้ตั้ง `trustedProxy`) ตรงกับที่ผู้ดูแลบอก: tunnel นี้ชี้ไปบริการอื่น ไม่ได้ชี้มาที่นี่

**สรุป: เซิร์ฟเวอร์โรงพยาบาลยังไม่ได้เปิดสู่อินเทอร์เน็ต** ความเสี่ยงเรื่องบัญชีไม่มี 2FA ยังจำกัดอยู่ใน LAN ตามเดิม

### สิ่งที่เปลี่ยนไปจากเดิม: งานที่เหลือสั้นลงมาก

โครงสร้างพร้อมหมดแล้ว — มีบัญชี Cloudflare มีโดเมน `kpsnana.com` มี tunnel ที่ต่อติดและพิสูจน์แล้วว่าเสถียรพอรับงานจริง **เหลือแค่เพิ่ม route ใหม่หนึ่งเส้น** ไม่ต้องติดตั้งอะไร ไม่ต้องรีสตาร์ตอะไร

### ข้อควรระวังของการใช้ tunnel ร่วมกับระบบอื่น

- **การเพิ่ม route เป็นการเพิ่ม ไม่ใช่การแก้ของเดิม** route แต่ละเส้นเป็นอิสระต่อกัน เพิ่ม `remote.kpsnana.com` ไม่กระทบระบบจองคิว
- tunnel แบบ token จะรับ config ใหม่จาก Cloudflare เอง **ไม่ต้องรีสตาร์ต service** — และไม่ควรรีสตาร์ตด้วย
- **แต่ต่อจากนี้ SCP-Remote จะพึ่ง tunnel เส้นเดียวกับระบบจองคิว** ถ้า tunnel ล่ม ทุกอย่างล่มพร้อมกัน — รวมถึงช่องทางที่จะรีโมตเข้าไปแก้ ให้คง `192.168.2.25:8443` ใน LAN ไว้เป็นทางสำรองเสมอ
- ก่อนตั้ง Access ให้ตรวจว่ามี Access application เดิมที่ครอบ `*.kpsnana.com` หรือทั้งโซนอยู่แล้วหรือไม่ ถ้ามี นโยบายนั้นจะครอบ `remote.kpsnana.com` ไปด้วยโดยไม่ได้ตั้งใจ

### 🔑 บัญชี Cloudflare กลายเป็นกุญแจของคอมพิวเตอร์โรงพยาบาล

เรื่องนี้เพิ่งเป็นเรื่องใหญ่เมื่อ SCP-Remote มาอยู่บน tunnel เดียวกับระบบสาธารณะ

ใครที่เข้าบัญชี Cloudflare `your-email@example.com` ได้ **สามารถแก้ route ให้ชี้ไปที่ไหนก็ได้ หรือปลด Access policy ทิ้งได้ทั้งหมด** — นั่นคือเปิดทางเข้าคอมพิวเตอร์ 91 เครื่องในโรงพยาบาล โดยไม่ต้องแตะเซิร์ฟเวอร์เลยสักนิด ต่อให้ MeshCentral บังคับ 2FA ไว้ก็ตาม

**บัญชี Cloudflare ต้องแข็งแรงอย่างน้อยเท่ากับบัญชี admin ของ SCP-Remote**

- เปิด 2FA ของบัญชี Cloudflare (My Profile → Authentication → Two-Factor Authentication)
- เก็บ recovery codes ไว้ที่ปลอดภัยนอกเครื่อง
- อีเมลที่ผูกบัญชีก็ต้องมี 2FA ด้วย เพราะรีเซ็ตรหัสผ่านผ่านอีเมลได้
- ถ้ามีคนใช้บัญชีนี้ร่วมกันหลายคน ให้แยกเป็น member รายคนแทน (Manage account → Members) เวลามีเรื่องจะรู้ว่าใครทำ

> เท่ากับตอนนี้มีสามด่านที่ต้องแข็งพอกัน: บัญชี Cloudflare, Cloudflare Access, และบัญชี SCP-Remote — อ่อนด่านใดด่านหนึ่งก็พอ

## ⭐ ทาง ก — Cloudflare Tunnel (แนะนำ)

ติดตั้ง `cloudflared` บนเครื่องเซิร์ฟเวอร์ มันเปิดการเชื่อมต่อ **ออก** ไปหา Cloudflare แล้ว Cloudflare ส่งคนที่เข้าชื่อโดเมนของเรากลับมาตามท่อนั้น

- **ไม่ต้องเปิดพอร์ตเข้าเลย** ไม่ต้อง port forward ไม่ต้องมี IP จริง — ไฟร์วอลล์ขาเข้ายังปิดสนิทเหมือนเดิม
- ได้ใบรับรอง TLS จริงฟรี เบราว์เซอร์ไม่เตือน
- คั่น **Cloudflare Access** (บังคับล็อกอินอีเมล/SSO ก่อนถึงหน้าเว็บ) ได้อีกชั้น — ต้องยกเว้นเส้นทาง `/agent.ashx` ไว้ เพราะเอเจนต์ล็อกอินอีเมลไม่ได้
- **ต้องมี:** ชื่อโดเมนที่ย้าย DNS มาไว้ที่ Cloudflare (โดเมนราคาไม่กี่ร้อยบาทต่อปี)

### ทาง ข — VPN

ปลอดภัยที่สุดและไม่เพิ่มช่องทางใหม่เลย แต่แก้ได้แค่ข้อเดียวจากสามข้อข้างบน — **เจ้าหน้าที่ IT ต่อ VPN ได้ แต่เครื่อง รพ.สต. กับโน้ตบุ๊กที่ออกนอกยังต่อไม่ได้** เว้นแต่จะให้ทุกเครื่องต่อ VPN ตลอดเวลา ซึ่งดูแลยากกว่ามาก

เหมาะเป็นทางเสริม ไม่ใช่ทางหลักของงานนี้

### ทาง ค — Port forward + Let's Encrypt

ทำได้ ในเครื่องมี `letsencrypt.js` และ `crowdsec.js` รองรับอยู่แล้ว แต่เป็นการเอาเซิร์ฟเวอร์ที่คุมคอมพิวเตอร์โรงพยาบาล 91 เครื่องไปวางหน้าอินเทอร์เน็ตตรง ๆ จะโดนสแกนและลองเดารหัสตลอดเวลานับตั้งแต่ชั่วโมงแรก

**ถ้าเลี่ยงไม่ได้จริง ๆ** ต้องมีครบทุกข้อ: `force2factor` เปิด, crowdsec ทำงาน, ใบรับรองจริง, และดู log การล็อกอินล้มเหลวสม่ำเสมอ

## สิ่งที่ต้องเปลี่ยนฝั่งเซิร์ฟเวอร์ (ตรวจกับโค้ดจริงแล้ว)

### 1. `trustedProxy` — ไม่ตั้ง = บันทึกการใช้งานเสียหมด

`cloudflared` รันอยู่บนเครื่องเซิร์ฟเวอร์เอง แล้วต่อเข้าหา MeshCentral จาก `127.0.0.1` ฉะนั้น**ทุกคนจากอินเทอร์เน็ตจะดูเหมือนมาจาก 127.0.0.1** ทั้งหมด — log การล็อกอิน บันทึกว่าใครเข้าเครื่องไหน ทุกอย่างจะชี้ไปที่ loopback เหมือนกันหมด ใช้สืบอะไรไม่ได้เลย

MeshCentral แก้ให้แล้วถ้าบอกมัน: [webserver.js:7215](../webserver.js#L7215) อ่านหัว `cf-connecting-ip` (ของ Cloudflare โดยเฉพาะ) แล้วถอยไป `x-forwarded-for` **แต่จะอ่านก็ต่อเมื่อ `trustedProxy` ตรงกับที่มาของการเชื่อมต่อ**

```json
"trustedProxy": "127.0.0.1"
```

> ปลอดภัยเพราะมีแต่ตัวเซิร์ฟเวอร์เองที่เป็น `127.0.0.1` ได้ คนอื่นปลอมหัว `x-forwarded-for` มาแล้วไม่มีผล

### 2. allowlist — จุดที่ต้องตัดสินใจอย่างรู้ตัว

ทุกวันนี้ `userAllowedIP`/`agentAllowedIP` คือ **รั้วจริง** ของระบบ รหัสผ่านที่หลุดไปไม่มีประโยชน์กับคนที่ไม่ได้อยู่ในเครือข่ายโรงพยาบาล

พอตั้ง `trustedProxy` แล้ว เซิร์ฟเวอร์จะเห็น IP จริงของคนที่ต่อจากบ้าน ซึ่ง**ไม่มีวันอยู่ใน allowlist** (IP บ้าน/มือถือเปลี่ยนตลอด) → เข้าไม่ได้ ฉะนั้นต้องเปิด allowlist กว้าง

**นั่นแปลว่ารั้วเดิมหายไป** สิ่งที่มาแทนคือ:

1. **Cloudflare Access** — บังคับล็อกอินอีเมล/SSO ก่อนถึงหน้าเว็บด้วยซ้ำ
2. **`force2factor`** — รหัสผ่านอย่างเดียวไม่พอ

ทั้งสองอย่างต้องพร้อมก่อน ไม่ใช่ทำทีหลัง

> `npm run check:config` บังคับลำดับนี้ให้แล้ว: ถ้าเจอว่า config เปิดสู่ภายนอก (ตั้ง `trustedProxy` หรือ allowlist กว้าง) แต่ยังไม่บังคับ 2FA หรือยังมีบัญชีที่ไม่ได้ตั้ง Authenticator **มันจะขึ้น "ยังไม่พร้อมเปิดใช้" และคืนค่า error** รันก่อนเริ่มบริการใหม่ทุกครั้ง

### 3. `/agent.ashx` ต้องไม่ติด Cloudflare Access

เอเจนต์ไม่มีเบราว์เซอร์ ล็อกอินอีเมลไม่ได้ ถ้าเอา Access ครอบทั้งโดเมน เครื่องลูกจะต่อไม่ได้ทั้งหมด — ตั้ง Access เฉพาะเส้นทางหน้าเว็บ และยกเว้น `/agent.ashx` ไว้ (ตัวมันมีการยืนยันตัวตนด้วยใบรับรองของมันเองอยู่แล้ว)

บัญชี Cloudflare: `your-email@example.com` โดเมน **`kpsnana.com`** ใช้ชื่อตัวอย่างว่า `remote.kpsnana.com`

### 1. Route ของ tunnel

**Networking → Tunnels →** เลือก tunnel **→ Routes → Add route → Published application**

| ช่อง | ค่า | ทำไม |
| --- | --- | --- |
| Hostname | `remote` . `kpsnana.com` | |
| Service URL | `https://localhost:8443` | `cloudflared` อยู่เครื่องเดียวกับเซิร์ฟเวอร์ (ใบรับรองมี SAN `localhost`) |
| Origin Server Name | เว้นว่าง | ชื่อใน Service URL ตรงกับใบรับรองแล้ว และ TLS ใช้ IP เป็น SNI ไม่ได้ |
| CA Pool | `C:\ProgramData\cloudflared\scp-remote-root.crt` | สำเนาของ `root-cert-public.crt` — ไม่ใส่จะได้ 502 |
| Disable TLS certificate verification | **ปิดไว้** | |

**ไม่ต้องปิดการตรวจ TLS** ใบรับรองของเซิร์ฟเวอร์ (`webserver-cert-public.crt`) มี SAN ครอบ `127.0.0.1` และ `localhost` อยู่แล้ว และออกโดย `MeshCentralRoot-e68095` ซึ่งอยู่ในไฟล์ `root-cert-public.crt` — ชี้ CA Pool ไปที่ไฟล์นั้นก็ตรวจผ่านครบ

> ใช้ `noTLSVerify` เฉพาะตอนไล่ปัญหาชั่วคราวเท่านั้น แล้วปิดกลับ

### 2. Access — ยกเว้น 4 เส้นทางที่เอเจนต์ใช้ ไม่ใช่แค่ `agent.ashx`

ตรวจในโค้ดแล้ว **เอเจนต์ไม่ได้ใช้แค่ `/agent.ashx`** — `agents/meshcore.js` ต่อเข้า `meshrelay.ashx?id=...` เองตอนเปิดเซสชัน ถ้าเอา Access ครอบทั้งโดเมน **หน้าจอรีโมตจะเปิดไม่ขึ้นทั้งระบบ** แม้เครื่องจะยังขึ้นออนไลน์

เส้นทางที่ต้องให้ผ่านโดยไม่ต้องล็อกอิน:

| เส้นทาง | ใช้ทำอะไร |
| --- | --- |
| `/agent.ashx` | ช่องสัญญาณหลักของเอเจนต์ |
| `/meshrelay.ashx` | เอเจนต์ต่อเข้ามาเมื่อเปิดหน้าจอ/เทอร์มินัล |
| `/agenttransfer.ashx` | รับ–ส่งไฟล์ |
| `/agentdownload.ashx` | เอเจนต์ดึงโมดูลรุ่นใหม่ |

**Zero Trust → Access → Applications** สร้าง 2 ชุด (path ที่เจาะจงกว่าชนะ)

1. **Self-hosted** โดเมน `remote.kpsnana.com` + path ข้างบนแต่ละอัน → policy **Bypass / Everyone**
2. **Self-hosted** โดเมน `remote.kpsnana.com` (ทั้งโดเมน) → policy **Allow** เฉพาะอีเมลของเจ้าหน้าที่

ทั้งสี่เส้นทางยังมีการยืนยันตัวตนของ MeshCentral เองอยู่ (ใบรับรองเอเจนต์ / คุกกี้ relay) การ bypass นี้แค่ไม่บังคับ "ล็อกอินอีเมล" ซึ่งเอเจนต์ทำไม่ได้อยู่แล้ว

### 3. ฝั่งเซิร์ฟเวอร์ — ใช้คำสั่งเดียว ไม่ต้องแก้ JSON เอง

มีสี่ค่าที่ต้องขยับ**พร้อมกันและถูกลำดับ** (`trustedProxy`, `userAllowedIP`, `agentAllowedIP`, `force2factor`) แก้ด้วยมือผิดจังหวะสองแบบมีราคาแพง: บังคับ 2FA ก่อนแอดมินลงทะเบียน = ล็อกตัวเองออกจากเซิร์ฟเวอร์ตัวเอง, เปิด allowlist ก่อนมี 2FA = เหลือรหัสผ่านกั้นเครื่อง 91 เครื่อง

```
npm run tunnel:mode            ดูสถานะปัจจุบัน
npm run tunnel:mode enable     เปิดโหมด tunnel
npm run tunnel:mode disable    ย้อนกลับเป็น LAN อย่างเดียว
```

`enable` จะ **ปฏิเสธและไม่แตะไฟล์เลย** ถ้ายังมีบัญชีที่ไม่ได้ตั้ง Authenticator — พร้อมบอกชื่อบัญชีนั้น และจะสำรองไฟล์ตั้งค่าเดิมไว้ทุกครั้งที่เปลี่ยนจริง

`disable` คืน allowlist เดิมกลับมาครบ (เก็บสำเนาไว้ใน `settings.scpLanAllowlist`) แต่ **คงการบังคับ 2FA ไว้** — ตั้งใจ เพราะตอนนั้นทุกคนลงทะเบียนแล้ว ปิดกลับมีแต่ทำให้อ่อนลง

> **ไม่แตะไฟร์วอลล์เลย** tunnel เข้ามาทาง `127.0.0.1` จึงไม่ต้องเปิดพอร์ตขาเข้าเพิ่ม ซึ่งเป็นเหตุผลหลักที่เลือกวิธีนี้ตั้งแต่แรก

จากนั้น

```
npm run check:config        ต้องไม่ขึ้น "ยังไม่พร้อมเปิดใช้"
npm run service:restart     แล้วยืนยันว่า PID เปลี่ยนจริง
```

### 4. เครื่องนอกโรงพยาบาล

เฉพาะเครื่องที่อยู่นอก **ขณะที่ยังต่ออยู่ใน LAN** สั่งผ่านคอนโซลของหน้าเว็บ

```
msh set MeshServer "wss://remote.kpsnana.com/agent.ashx"
service restart
```

**เครื่องในโรงพยาบาลไม่ต้องแตะ** ปล่อยให้ใช้ `wss://192.168.2.25:8443/agent.ashx` ต่อไป

---

## ⚠️ กับดักที่ทำให้เครื่องหลุดทั้ง 91 เครื่อง

เอเจนต์ผูกกับเซิร์ฟเวอร์ด้วยสองค่า (ดู [MOVING-THE-SERVER.md](MOVING-THE-SERVER.md))

| ค่า | ตอนนี้ | ถ้าเปลี่ยนผิด |
| --- | --- | --- |
| `MeshServer` | `wss://192.168.2.25:8443/agent.ashx` | ต่อไม่ติด เครื่องหายจากระบบ |
| `ServerID` | แฮชของ `agentserver-cert-public.crt` | ต่อติดแต่ไม่เชื่อถือ ปฏิเสธการเชื่อมต่อ |

**`agentserver-cert-public.crt` ห้ามเปลี่ยนเด็ดขาด** ถ้าเปลี่ยน ต้องเดินไปลงเอเจนต์ใหม่ทีละเครื่องทั้ง 91 เครื่อง

โชคดีที่ **ใบรับรองของหน้าเว็บกับ `agentserver-cert` เป็นคนละใบ** — เปลี่ยนใบเว็บเป็นโดเมนจริงได้โดยเอเจนต์ไม่สะเทือน ตราบใดที่ไม่ไปแตะไฟล์ `agentserver-cert-*`

### เครื่องในโรงพยาบาลควรใช้ทางไหน

**อย่าย้ายเครื่องใน LAN ไปใช้ชื่อโดเมนสาธารณะ** ถ้าทำ ภาพหน้าจอของเครื่องที่อยู่ห่างกันสองเมตรจะวิ่งออกอินเทอร์เน็ตไปกลับ กินแบนด์วิดท์ขาออกของโรงพยาบาลและช้าลงโดยไม่ได้อะไร

- เครื่องใน LAN → คง `wss://192.168.2.25:8443/agent.ashx` ไว้เหมือนเดิม
- เครื่องนอก (รพ.สต., โน้ตบุ๊กที่ออกนอก) → ใช้ชื่อโดเมนสาธารณะ

เปลี่ยน URL ของเครื่องที่ออกนอกได้จากหน้าเว็บโดยไม่ต้องเดินไปหา **ขณะที่เครื่องนั้นยังต่ออยู่ใน LAN**

```
msh set MeshServer "wss://<โดเมน>/agent.ashx"
service restart
```

> ทำตอนเครื่องยังอยู่ใน LAN เท่านั้น ถ้าสั่งตอนอยู่ข้างนอกแล้วพลาด จะติดต่อกลับไม่ได้อีก

## ลำดับงานที่แนะนำ

1. ตั้ง 2FA ให้ admin + เก็บรหัสสำรอง ← **ทำก่อนเสมอ**
2. สร้างบัญชีรายคนให้เจ้าหน้าที่ แล้วเปิด `force2factor`
3. จดโดเมนและย้าย DNS ไปที่ Cloudflare
4. ติดตั้ง `cloudflared` บนเซิร์ฟเวอร์ ชี้ไปที่ `https://192.168.2.25:8443`
5. เปิด Cloudflare Access คั่นหน้าเว็บ ยกเว้น `/agent.ashx`
6. ทดสอบจากมือถือที่ปิด WiFi (ใช้เน็ตมือถือ) ว่าเปิดหน้าเว็บและรีโมทได้
7. ทดลองกับ **เครื่องเดียว** ที่เตรียมย้อนกลับได้ ก่อนแตะ รพ.สต.
8. ค่อยทยอยย้ายเครื่องนอกอาคาร

## ยังไม่ได้ตรวจ — ต้องถามทีมเครือข่าย

- อินเทอร์เน็ตขาออกของโรงพยาบาลกว้างเท่าไหร่ การรีโมทกินประมาณ 100–500 KB/s ต่อเซสชัน
- มีไฟร์วอลล์ที่บล็อก outbound หรือบังคับ proxy ไหม (มีผลกับ `cloudflared`)
- นโยบายความปลอดภัยของโรงพยาบาลเรื่องการเข้าถึงจากภายนอก ต้องขออนุมัติใครก่อน
