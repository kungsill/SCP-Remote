# ช่องโหว่ dependencies ที่รอ upstream จดไว้ 2026-10-15

เอกสารนี้จดช่องโหว่ dependencies ที่รู้อยู่ (npm audit) ที่**แก้ไม่ได้ในวันที่จด** เพราะไม่มี
เวอร์ชันที่แก้แล้วให้ใช้ หรือแก้แล้วต้องเปลี่ยนเวอร์ชันแบบ breaking จึงต้องรีวิวก่อนรัน
ผู้รับช่วงอ่านหัวข้อนี้ก่อนตัดสินใจอัปเดต และ**เลือกแค่ทางเดียวต่อรายการ: รอ upstream หรือ
อัปเดตพร้อมรีวิว**

ผลตรวจที่พิมพ์ได้เสมอ: `npm audit --omit=dev`

ที่มาของข้อตัดสิน: การตรวจสอบวันที่ 15 ตุลาคม 2569 — ตรวจ syntax ทุกไฟล์ JS (406 ไฟล์)
รันเทสต์ระบบ 559 รายการ ตรวจ `npm audit` แล้วแก้ส่วนที่แก้ได้ทันทีด้วย `npm audit fix`
และรีวิวโค้ดส่วนของ SCP-Remote ทั้ง hospital/ และ scripts/ ไม่พบบั๊กที่ต้องแก้
เอกสารอื่นที่อ่านก่อนลงมืออยู่ใน [รับช่วงดูแล SCP-Remote](HANDOVER.md)

## รายละเอียดรายตัว

### node-forge 1.4.0 — high, ไม่มี fix วงการ

- **advisory**: [GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv) —
  การเช็คลายเซ็น RSA PKCS#1 v1.5 ยอมรับอิลิเมนต์ DigestAlgorithm ที่ซ้อนเกินจำเป็น
- **ในระบบนี้มันใช้ทำอะไร**: ใบรับรอง/การเข้ารหัสของ MeshCentral (`certoperations.js`,
  `letsencrypt.js` และเว็บเซิร์ฟเวอร์) ไม่เกี่ยวกับโค้ด hospital ที่ทีมเขียนเอง
- **ทำไมถึงรอ**: `npm audit fix` ไม่ผล เพราะยังไม่มีรุ่นที่แก้ advisory นี้โพสต์ออกมา
  การเขียนโค้ดบังคับ patch เองมีแต่เสี่ยงกับระบบใบรับรอง
- **อันตรายเมื่อไร**: เมื่อมีผู้โจมตีปลอมลายเซ็นดิจิทัลโดยอาศัยข้อบกพร่วงนี้ ซึ่งต้องโจมตีเชิงลึก
  และไม่เกี่ยวกับการเปิดพอร์ต 8443 ให้วง LAN ตามที่ระบบนี้ใช้
- **กลับมาดูเมื่อ**: มีรุ่น node-forge ใหม่โพสต์แก้ advisory นี้ จึงอัปเดตและรัน
  `npm run test:hospital` ยืนยัน

### compression 1.8.1 — high, fix ต้องถอด pin

- **advisory**: [GHSA-vc2v-76pw-4v95](https://github.com/advisories/GHSA-vc2v-76pw-4v95) —
  ปิด response ก่อนเสร็จอาจทำ memory leak จน DoS
- **ในระบบนี้มันใช้ทำอะไร**: compression middleware ของ express ใน webserver.js ใช้กับ page
  ทุก response — ต้องมี client ปิดการเชื่อมต่อแบบนั้นจึงถึงขั้นเรียกเป็น risk ระดับ high
- **ทำไมถึงรอ**: fix คือ 1.8.2 แต่ `package.json` pin เป๊ะ `{ "compression": "1.8.1" }`
  ทุกรายการใน dependencies ของโปรเจกต์นี้ pin เป๊ะ — ถอด pin เป็น `^1.8.2` คือการเปลี่ยน
  policy เวอร์ชัน ซึ่งต้องพิจารณาให้ครบทั้งไฟล์ ไม่ใช่เปลี่ยนเฉพาะตัวนี้
- **อันตรายเมื่อไร**: มี client ปิดการเชื่อมต่อกลางคันจำนวนมากซ้ำ ๆ จน server โดน leak หนัก
  ซึ่งต้องเป็นผู้ใช้ในวง LAN ที่ตั้งใจรบกวน ไม่ใช่คนทั่วไปจากอินเทอร์เน็ต
- **กลับมาดูเมื่อ**: ตัดสินใจถอด pin เป็น `^1.8.2` แล้วเทียบทั้งไฟล์ + รัน test:hospital

### node-windows 0.1.14 (ผ่าน minimist) — critical, ต้องเปลี่ยนรุ่นแบบ breaking

- **advisory**: [GHSA-vh95-rmgr-6w4m](https://github.com/advisories/GHSA-vh95-rmgr-6w4m) และ
  [GHSA-xvch-5gv4-984h](https://github.com/advisories/GHSA-xvch-5gv4-984h) —
  prototype pollution ใน minimist รุ่นเก่า (<=0.2.3) ซึ่งดึงมาผ่าน optimist
- **ในระบบนี้มันใช้ทำอะไร**: `scripts/service-hospital.js` ใช้ node-windows ลงและคุมบริการ
  Windows (`SCP-Remote` service) — **ใช้ตอนพิมพ์คำสั่งเท่านั้น รันในเครื่องตัวเอง** ไม่รับ
  อินพุตจากเครือข่ายเลย
- **ทำไมถึงรอ**: รุ่นแก้อยู่ `1.0.0-beta.8` ซึ่งเปลี่ยน API ใหญ่ (breaking) และยังเป็น beta —
  ใช้ beta กับระบบบริการโรงพยาบาลไม่ควรเสี่ยง และต้องปรับ `scripts/service-hospital.js`
  เพราะ API ตัวคุมบริการเปลี่ยนไปด้วย
- **อันตรายเมื่อไร**: แทบไม่มี — minimist อยู่ใน chain ที่ไม่เคย parse อินพุตจากภายนอก
  node-windows ใช้เฉพาะตอนพิมพ์คำสั่งดูแลบริการในเครื่องเซิร์ฟเวอร์เอง
- **กลับมาดูเมื่อ**: node-windows ปล่อยรุ่น stable >0.1.14 ที่เลิก optimist/minimist จึง
  อัปเดตและทดสอบ install/uninstall/restart บริการด้วยมือทั้ง `service:install` และ
  `uninstall` และ `service:restart` ทั้งขั้นตอน

## เมื่อ upstream มรุ่นใหม่แล้ว ทำอย่างนี้

1. `npm audit --omit=dev` ดูว่ารายการไหนหายไป
2. แก้รายการนั้น (ถอด pin เฉพาะที่จำเป็น) แล้วอัปเดตตารางในเอกสารนี้
3. `npm run test:hospital` ต้องผ่านทุกเทส
4. ถ้าแตะ node-windows: ทดสอบ `service:install → start → stop → uninstall` ทั้งชุด
5. ถ้าแตะ node-forge: ทดสอบเข้าเว็บ 8443 ผ่านใบรับรองจริง + `npm run check:hospital`
6. ถ้าแตะ compression: ตรวจ `check:hospital` ว่า compression ยังบีบอัดหน้าเว็บได้
7. อัปเดตกราฟสถานะในหัวข้อ "สรุปสถานะ" และวันที่ตรวจล่าสุดไว้ตรงหัวเอกสาร

## ทำไมเลือกรอ

ช่องโหว่ที่เหลือแต่ละตัวยังมีจุดอ่อนจริง แต่ถึงขั้นถูกทำร้ายได้ต้องผ่านเงื่อนไขที่ตั้งค่าระบบนี้
ปิดไว้อยู่แล้ว:

- ระบบฟังเฉพาะวง LAN ที่อนุญาตไว้ (12 วง) ไม่เปิดออกอินเทอร์เน็ต (`npm run check:config`
  ยืนยันทุกครั้งที่รัน)
- minimist/node-windows ใช้เฉพาะตอนพิมพ์คำสั่งดูแล ในเครื่องเดียว ไม่เห็นเครือข่าย
- node-forge ใช้กับใบรับรองของเซิร์ฟเวอร์ ไม่ได้เปิดรับคำขอจากภายนอกโดยตรง
- เทสคุมเกือบทุกชั้น (559 เทส) และ `check:hospital` ยืนยันหน้าเว็บเสิร์ฟได้จริง

ถ้าเอาเข้าอินเทอร์เน็ตทีหลัง (tunnel-mode enable หรือเปลี่ยน allowlist กว้างขึ้น)
**กลับมาอ่านเอกสารนี้ก่อน** และพลิกการตัดสินใจใหม่ เพราะระดับเสี่ยงที่คำนวณไว้ในเอกสารนี้
สมมติว่าระบบยังอยู่ใน LAN เท่านั้น
