**แก้แล้ว 20 กันยายน 2569** ผู้ดูแลเลือกแนวทาง ก. ตอนนี้ `main.js` ตรวจสอบใบรับรองระดับ session ซึ่งครอบคลุม WebSocket ยอมรับเฉพาะที่ปักหมุดไว้ ทดสอบแล้วต่อจอได้จริงและแถบหยุดขึ้น สร้างตัว .exe และไฟล์ zip ใหม่แล้ว

บันทึกทางเลือกไว้เผื่ออนาคตเปลี่ยนใบรับรองหรือย้ายเซิร์ฟเวอร์:

| แนวทาง | ต้องทำอะไร | ข้อดี | ข้อเสีย |
| --- | --- | --- | --- |
| **ก. ปักหมุดใบรับรองในโปรแกรม** | แก้ `main.js` ให้ตรวจสอบใบรับรองระดับ session โดยยอมรับเฉพาะ hostname และลายนิ้วมือ SHA-256 ที่ปักหมุดไว้ ส่วนที่เหลือปล่อยให้ Chromium ตัดสินตามปกติ แล้ว build ใหม่ | ไม่ต้องแตะเครื่องเจ้าหน้าที่เลย ใช้โมเดลความปลอดภัยเดียวกับที่โปรแกรมใช้อยู่แล้วกับการโหลดหน้าเว็บ | มีโค้ดตรวจใบรับรองเองในโปรแกรม ต้องแก้ทุกครั้งที่เปลี่ยนใบรับรองเซิร์ฟเวอร์ |
| **ข. ติดตั้งใบรับรองเซิร์ฟเวอร์เป็น Trusted Root** | นำใบรับรองของเซิร์ฟเวอร์ไปติดตั้งในที่เก็บใบรับรองที่เชื่อถือได้ของเครื่องที่รันโปรแกรม | ไม่ต้องแก้โค้ดเลย Chromium ตรวจสอบเองตามมาตรฐาน เป็นวิธีที่องค์กรทั่วไปใช้ | ต้องไปตั้งค่าทุกเครื่องที่ใช้โปรแกรม และการเพิ่ม Trusted Root มีน้ำหนักด้านความปลอดภัยของตัวมันเอง |
| **ค. ใช้ใบรับรองที่ออกโดย CA จริง** | ตั้งชื่อโดเมนภายในให้เซิร์ฟเวอร์และขอใบรับรองที่เชื่อถือได้ | สะอาดที่สุดระยะยาว ทุกเบราว์เซอร์และทุกโปรแกรมยอมรับเอง | ต้องวางระบบ DNS และ PKI ก่อน ใช้เวลามากที่สุด |

ใบรับรองปัจจุบันของเซิร์ฟเวอร์มีอายุถึงปี 2049 และลายนิ้วมือตรงกับที่ปักหมุดไว้ในโปรแกรมแล้ว

### 2.4 กับดักร้ายแรง: `service:restart` รายงานว่าสำเร็จทั้งที่ไม่ได้รีสตาร์ต ✅ แก้แล้ว

พบ 20 กันยายน 2569 หลังไล่หาว่าทำไมแก้ `agents/meshcore.js` แล้วเครื่องลูกไม่ได้ core ใหม่

**อาการ** `npm run service:restart` พิมพ์ว่า `SCP-Remote service stopped.` แล้ว `SCP-Remote service started.` ทุกครั้ง แต่ **process ของเซิร์ฟเวอร์ยังเป็น PID เดิม** เครื่องลูกก็ยังต่ออยู่ตลอดโดยไม่หลุด ทำให้ดูเหมือนรีสตาร์ตสำเร็จ

**สาเหตุจริง** บริการ Windows `scpremote.exe` อยู่ในสถานะ **Stopped** แต่ process ลูก (node 3 ตัว) ยังรันค้างเป็น orphan และยังจองพอร์ต 8443 อยู่ ตัวที่สั่ง start ใหม่จึงจองพอร์ตไม่ได้และตายไป เหลือ orphan เสิร์ฟงานต่อด้วย **โค้ดรุ่นเก่าที่โหลดไว้ตั้งแต่ตอนบูต**

**ผลที่ตามมา** การแก้ไฟล์ฝั่งเซิร์ฟเวอร์ทุกอย่างไม่มีผล ทั้งที่ทดสอบผ่านและเอกสารบอกว่า deploy แล้ว อันตรายเพราะไม่มีสัญญาณเตือนใด ๆ

**วิธีตรวจก่อนเชื่อว่า deploy สำเร็จ** ดูว่า PID เปลี่ยนจริงไหม:

```
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -like '*sichomphu-remote*' } |
  Select-Object ProcessId, CreationDate
Get-Service scpremote.exe | Select-Object Name, Status
```

ถ้าบริการเป็น `Stopped` แต่ยังมี process อยู่ = เจอกรณีนี้ **วิธีแก้:** ปิด process ที่ค้างทั้งหมด (ลูกก่อนแม่) ตรวจว่าพอร์ต 8443 ว่าง แล้วค่อย `npm run service:start`

หลังเก็บกวาดแล้ว เครื่องลูก 21 จาก 22 เครื่องได้ core ใหม่ภายในไม่กี่วินาที ยืนยันว่ากลไก push core ทำงานปกติมาตลอด ปัญหาอยู่ที่เซิร์ฟเวอร์ไม่เคยรีสตาร์ตจริง

### 2.5 ถอน ESET ที่ ARI — งานหน้างาน ไม่ใช่งานโค้ด

ESET หมดสัญญา ไม่อัปเดตมา 3-4 ปี ต้องการถอดออกเพื่อให้ Windows Defender รับช่วง มี **2 เครื่องเท่านั้น** ในระบบ

| เครื่อง | IP | สถานะ |
| --- | --- | --- |
| **ARI พยาบาล** | 192.168.7.71 | กู้ออกจาก Safe Mode แล้วเย็น 19 ก.ย. (Agent กลับมา 18:39) ใช้งานปกติ แต่ยังมี ESET ลงทะเบียนซ้ำ 3 ครั้ง ยังไม่ได้ถอน |
| **ARI เครื่อง หมอ** | 192.168.7.106 | ออนไลน์ มี ESET 1 ตัว Windows แจ้ง PROBLEM |

**ARI พยาบาล กลับมาใช้งานปกติแล้ว** ผู้ดูแลไปกู้ออกจาก Safe Mode ที่เครื่องเองเมื่อเย็นวันที่ 19 ก.ย. แต่ยังไม่ได้ถอน ESET (เดิมตั้ง `safeboot network` ไว้แล้วและเครื่องบูตเข้า Safe Mode แต่ Agent ไม่ขึ้น (ดูข้อ 3.1) เข้าไม่ได้จากรีโมต ที่เครื่องมี `C:\Windows\Temp\uninstaller.exe` (ESETUninstaller v10.54.33.0 ของแท้) เตรียมไว้แล้ว

ขั้นตอนที่เครื่อง:

1. ล็อกอินด้วยบัญชีสิทธิ์ admin
2. เปิด Command Prompt แบบ Run as administrator
3. `bcdedit /deletevalue {default} safeboot` — **ต้องทำก่อน** ไม่งั้นเครื่องวนกลับเข้า Safe Mode ตลอด
4. `C:\Windows\Temp\uninstaller.exe` แล้วทำตามที่มันถาม
5. รีสตาร์ต เครื่องจะกลับเข้าโหมดปกติ Defender เปิดเอง
6. เก็บกวาด (ไม่บังคับ): `reg delete "HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Network\Mesh Agent" /f`

**ARI เครื่อง หมอ** — ยังไม่ได้ทำอะไร **อย่าใช้วิธีรีโมต Safe Mode ซ้ำ** ถ้าจะถอน ให้ลองถอนโหมดปกติผ่าน `ตรวจโปรแกรม → ดูรายการ/ถอดออก` ก่อน (เสี่ยงต่ำ ไม่ต้องรีบูต) ถ้าไม่สำเร็จค่อยไปทำ Safe Mode **ที่เครื่อง**

## 3. บทเรียนหน้างาน — บันทึกไว้กันพลาดซ้ำ

### 3.1 Mesh Agent ไม่ขึ้นใน Safe Mode แม้จะลงทะเบียนไว้แล้ว

ทดลองจริงกับ ARI พยาบาล: เพิ่มคีย์

```
HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Network\Mesh Agent  (Default) = "Service"
```

ยืนยันว่าคีย์ติดจริงด้วย `reg query` แล้ว รีบูตด้วย `bcdedit /set {default} safeboot network` **ผลคือ Agent ไม่ต่อกลับมาเลยเกิน 100 นาที**

**สรุป: อย่าวางแผนทำงานรีโมตใน Safe Mode กับเครื่องโรงพยาบาล** เครื่องจะขาดการติดต่อและต้องเดินไปกู้ที่เครื่อง

### 3.2 Task Scheduler ก็ไม่ทำงานใน Safe Mode

`SafeBoot\Network` ไม่มีคีย์ `Schedule` ตามค่าเริ่มต้นของ Windows แปลว่า **แผนสำรองแบบ "ตั้ง scheduled task ให้ถอย safeboot อัตโนมัติ" ใช้ไม่ได้** ถ้าจะทำต้องเพิ่ม `Schedule` เข้า `SafeBoot\Network` ด้วย ซึ่งเพิ่มความซับซ้อนและจุดพังอีกจุด

### 3.3 ถ้าจำเป็นต้องทำ Safe Mode จริง ๆ

ทำที่เครื่อง หรือให้แน่ใจว่ามีคนเดินไปถึงได้ และ **เตรียมไฟล์ที่ต้องใช้ไว้ในเครื่องก่อนรีบูตเสมอ** (ที่ทำถูกในรอบนี้คืออัปโหลด `uninstaller.exe` ไว้ล่วงหน้า ทำให้แผนสำรองเหลือแค่เดินไปกด)
